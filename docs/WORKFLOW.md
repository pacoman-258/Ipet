# Neo Aspect Product Workflow

## Purpose

This file defines stable Ipet product contracts: state transitions, safety boundaries, and externally meaningful behavior. Implementation details, provider argument shapes, local paths, timeouts, and command construction belong in code and tests.

## Product Modules

- **Body** senses, speaks, renders, and executes authorized local actions.
- **Brain** chooses one next step for the current turn.
- **Human Ops** authorizes, records, executes, and verifies actions with side effects.
- **Memory & Skills** owns durable memory, preferences, summaries, and learned procedures.

`main.py`, `backend/app.py`, and `index.html` remain composition or loading entrypoints. Domain behavior belongs in the owning module.

## Turn Flow

```text
user input
  -> Body gathers bounded context
  -> Brain returns one decision
  -> Body renders a terminal reply, or Human Ops authorizes one proposal
  -> authorized work executes through the owning module
  -> Human Ops verifies every executed action
  -> when structured task state requests continuation, Brain receives a bounded result delta
  -> otherwise Body returns the verified terminal result
```

Brain never performs a side effect directly. A new side effect, changed target, or changed risk requires a new Human Ops proposal.

## Stop Authority

Active tasks use `running -> stopping -> stopped`. The chat send control becomes a stop control while Brain, Observe, approval waiting, or post-approval continuation is active; `Esc` and `Command + .` use the same local path.

Stop is handled locally and does not wait for Brain or the network. It prevents new work, aborts cancellable streams, invalidates queued proposals, and discards stale coordinate, focus, and surface assumptions. An atomic action already in flight may finish, but no continuation starts afterward.

Stopping does not roll back completed effects. The terminal summary separates completed, unexecuted, and uncertain actions and uses `已由用户停止` rather than a normal completion claim.

## Startup

- `main.py` composes the desktop shell and Qt lifecycle.
- `backend/app.py` registers the local FastAPI surface.
- Root UI entry paths remain stable until their loaders move in the same change.
- Body initializes the pet, voice services, and optional observation without blocking the first window on model readiness.
- Local Qwen TTS failure is explicit: the queue is cleared and browser speech is not used as a silent fallback.
- Memory & Skills loads local indexes; Human Ops initializes pending approval state.

Missing required configuration fails visibly and never erases user data. Qt entrypoint changes remain composition, registration, loading, lifecycle, or compatibility work.

## Observe And Present

Body gathers only context needed for the current turn: the request, bounded conversation state, allowed memory, optional screen evidence, voice state, and relevant UI state.

The idle desktop surface is a transparent, frameless Live2D pet without a persistent application shell. A fresh or invalid legacy layout places the model at the lower-right with an 18-pixel inset and fits it to roughly 38% of the host viewport height. The window remains above ordinary application windows; on macOS, its tool-window surface also stays visible when Finder or another application becomes active instead of hiding on application deactivation. Body constrains the window and saved model transform to the current viewport so an older offset cannot move the pet completely off-screen. The frontend reports bounded model, menu, and chat rectangles to Body, which applies them as the native window mask; desktop input outside those regions passes through to the underlying application instead of being captured by an invisible rectangle. Right-clicking the model opens the animated local menu for persistent conversation, temporary conversation, history, settings, and window controls. Persistent and temporary conversation choices create the corresponding new session only while conversation switching is safe. The history drawer keeps its existing topic semantics. Chat appears as a clean floating layer above the pet and uses the user-selected background inside that layer rather than painting the entire desktop window. Settings continues to open the separate WebUI configuration page. Closing settings or another auxiliary window destroys only that window; the desktop host exits only through the pet window's explicit shutdown path.

The chat worklog exposes curated events under eight categories: `planning`, `searching`, `observing`, `acting`, `waiting_approval`, `verifying`, `blocked`, and `completed`. It may show bounded Observe questions and structured evidence, but never raw chain-of-thought, hidden prompts, secrets, or unfiltered tool output. The panel stays open while active or blocked and collapses after completion.

Token counters use provider-reported input, output, and total usage. Providers without usage data do not trigger character-based estimates.

## Ambient Presence And Initiative

Ambient presence is a Body-owned enhancement, not a hidden autonomous task. It has three explicit modes: `off` collects nothing, `shadow` records bounded “would speak” event types without calling Brain or sending output, and `active` may deliver a proactive `say`. The default is `off`.

The metadata lane samples only foreground application and idle duration. Window titles are omitted at Body and stripped again by the backend unless the user explicitly enables them. Screen context is a separate opt-in; when disabled, ambient presence does not capture screenshots. Raw screenshots, OCR text, and environment events never enter conversation history or durable memory. Fresh frames and events are process-local, bounded, and expire.

Every event passes through the local privacy filter before frame storage or semantic analysis. Password managers, private browsing, financial, payment, medical, and identity contexts, plus user-configured blocked applications, become only `privacy_blocked`; their application, title, text, and image are not retained. Environment APIs accept only local trusted origins, and sensor/frame ingestion additionally requires the desktop local token.

The initiative gate converts allow-listed facts such as `user_returned`, `focus_milestone`, `test_passed`, or `build_failed` into opportunities. Confidence, per-kind and global cooldown, quiet hours, daily limit, client busy state, and unanswered-message backoff are checked before Brain. `neuro_like` intensity may also consider application changes; quieter levels do not. The settings audit explains queued, suppressed, shadowed, delivered, deferred, and privacy-blocked decisions without exposing captured text.

For an eligible opportunity, Brain receives bounded event facts as untrusted data plus normal persona and relationship context. Only `say` or `stop` is accepted; any observe, action, or memory decision is discarded. Frontend delivery rechecks chat, ASR, TTS, visibility, and recent user activity, then reports `delivered`, `deferred`, or `dismissed`. A delivered proactive utterance is not forged into `TopicStore`; it becomes one process-local reply context for the user's next message. Temporary conversations never receive proactive output or that context. Any side effect mentioned after a proactive exchange still requires its ordinary Human Ops proposal.

## Conversation Memory

Persistent conversations use bounded summaries and recent complete exchanges from `TopicStore`. Temporary conversations remain process-local, never read or write `TopicStore`, and cannot merge with a persistent session. Memory-mode switches are rejected while an older response or approval chain is active.

Long-term memory and learned procedures require explicit Human Ops review. Features without a verified review path must not write durable state.

Relationship memory follows one closed loop: detect a candidate, review it, persist only an approved record, retrieve a bounded relevant subset, and let the user correct or forget it. Explicit `propose_remember` decisions pause at Human Ops; rejection writes no memory. Post-turn extraction may create at most one non-blocking, process-local candidate and never persists it before approval. Temporary conversations neither retrieve long-term memory nor create candidates.

Approved records use the existing Markdown memory store and carry a stable id, kind, summary, source conversation and turn, visible reason, scope, sensitivity, status, retention/expiry, and optional follow-up time. Active, unexpired records alone are retrievable. A correction may supersede one unambiguous active record; superseded, resolved, expired, and forgotten records are never injected together with current facts. Forgetting removes the long-term memory file immediately; deleting the source conversation remains a separate user action.

Each persistent turn injects no more than five relevant approved records and no more than 1,200 characters as fact data, never as instructions. Direct text/topic matches outrank generic preference fallback. The pet uses a memory only when it naturally helps the current reply and does not mention it merely to prove recall.

An approved `open_loop` may become eligible for one gentle follow-up after its due time. Follow-ups respect the configured quiet hours and cooldown. Delivery to Brain is not counted as a completed follow-up unless the visible reply actually refers to the remembered topic. The user can resolve or snooze an open loop through a reviewed `propose_remember` status change or directly in the settings Memory console.

## Brain Decision Contract

Brain returns exactly one `BrainDecision`:

- `say`: answer or ask for user input.
- `think`: record bounded progress without side effects.
- `observe`: request bounded visual or local evidence.
- `propose_act`: hand one action to Human Ops for authorization.
- `propose_remember`: ask to review one durable memory write.
- `stop`: end with a terminal summary.

Providers are asked for one JSON object; plain text remains a compatibility `say`. Brain does not directly click, type, launch, write files, mutate settings, install software, or persist memory.

Decision kinds, action arguments, goal statuses, and profile allowlists come from one schema registry used by both prompt rendering and runtime validation. The model selects a route from the complete request semantics; user-text keywords may enrich an already selected observation, but cannot change a decision kind, authorize an action, override a terminal state, or force continuation. Coordinate-specific observation is explicit as `observe.require_coordinates=true`; mentioning words such as “click” or “coordinates” does not set it after parsing. Passive visual grounding and frame injection likewise require explicit request/configuration state rather than a visual-word dictionary.

### Computer Use

Computer-use action proposals are deliberately bounded: `playwright`, `launch_app`, `click`, `type_text`, and Enter/Return through `key_press`. Native click, text, and key proposals name `target_app`. A click binds either one complete reviewable coordinate pair or one opaque Accessibility element reference copied from the latest observation. Filesystem actions use the separate bounded schema listed under Execute.

macOS Accessibility support is dynamic rather than allowlisted. Body resolves any named regular GUI application against currently running applications using AppKit, with System Events and process metadata as fallbacks. QQ, WeChat, Music, and Finder retain compatibility aliases and specialized surface names, but do not define the support boundary. The complete Ipet host process tree is never an Accessibility target: discovery excludes the host PID and all descendants such as QtWebEngine helpers, capture and semantic-action entrypoints reject them again, and the native runtime refuses to create an application element for its own PID. This prevents a background AX refresh from synchronously re-entering Ipet's Chromium UI through a helper process. Frontmost identity prefers `NSWorkspace`; environments without PyObjC use System Events process metadata and never read the system-wide `AXFocusedApplication` from an Ipet worker thread. Resolved target PIDs are used before any optional frontmost lookup. This identity check never traverses the Ipet hierarchy, and the host-process-tree guard applies before any application tree is opened. When the product Accessibility permission is enabled and the Ipet host has macOS Accessibility trust, Body traverses an external application's complete exposed `AXUIElement` hierarchy up to a high fail-safe cap. Window content is traversed before menu descendants so a large application menu cannot consume the interactive budget before the requested page. Shared nodes and graph cycles are deduplicated with CoreFoundation element equality while their references remain alive for the traversal, so allocator address reuse cannot discard unrelated controls. Only size, depth, timeout, or child-list cutoffs mark a capture incomplete. Every visited node records whether its child list was completely enumerated and how many unique children were queued. The latest tree for each application is stored under ignored local state in `data/ax_trees/`, split into JSONL chunks behind an atomically replaced metadata pointer. Every stored node carries its hierarchy path, so the files preserve tree structure rather than only a flat model-facing result list. Only the current snapshot is retained; secure text values are removed both during capture and again at the storage boundary. Other visible application text may be present in this local index.

`observe.ax_query` is application-agnostic: Brain supplies a short query for the current `target_app`, which may match visible text, AX role, identifier, or supported action. Search lazily loads the persisted app tree and exposes only a compact role/action index plus a bounded semantic slice to Brain. For any read-only collection query, the slice includes the collection anchor plus label-only `collection_items` up to the 64-item cap, even when Brain names AX collection roles but omits words such as “all”; keeping names only inside the internal frame is not considered a successful observation. A process change, a native UI action, an explicitly stale snapshot, or the 30-second live-use TTL triggers refresh when observation needs that application; queries asking for the current collection, visible controls, focus, or selection always read the live tree. Interactive application reads allow six seconds for deep or virtualized collections to materialize their last AX child and keep an 18-second command deadline for one focused retry. An expired snapshot remains searchable as bounded read-only context, but is marked stale and has every executable reference withheld. A capture stopped by the fail-safe size or time limit remains globally incomplete. Search may still accept a narrower result when its declared collection count is exact, every direct collection child was captured, an entire target window was captured, or one unique visible non-chat target has a fully enumerated reviewed path. A read-only collection whose direct branch and labels are complete remains usable even when an unrelated part of the application tree reaches the fail-safe limit. This scoped result never claims that the whole application tree is complete; ambiguous, chat-message, expired, process-changed, or structurally unproven targets still withhold executable references and retry or fall back to pixels. A structurally proven spelling-near action target explicitly sets `visual_fallback_required=false`; the desktop router preserves that AX result without capturing pixels, and both initial and post-action continuation paths deterministically return `goal.status=need_user` with the bounded candidate labels instead of spending another multimodal Brain call or guessing the target. The natural-language observe question is only a compatibility fallback when an older Brain reply omits `ax_query`.

The settings Human Ops panel exposes index status and a manual refresh. Refresh enumerates currently running regular GUI applications, including hidden ones, up to a 128-application fail-safe and never launches or focuses them. The host PID is reported as self-excluded and is never handed to the AX runtime; any older matching snapshot is retained only as stale local state. The result explicitly marks discovery truncation if that cap is reached. At each terminal chat or Human Ops session event, Backend schedules the same refresh in the background; duplicate refreshes coalesce. Native AX calls are serialized across those background jobs and interactive observation/action calls, with waiting interactive work taking priority between background application captures. Each background application capture has a five-second budget, so an all-app refresh cannot monopolize the shared native AX channel with one slow application. A transient application-discovery failure is non-authoritative and does not mark every stored app as stopped. A background capture that exposes only menus, fewer windows, a materially smaller tree, or a completely different window signature does not overwrite the same-process main-window snapshot—even when the auxiliary window happens to contain more nodes. Window identity signatures and page-role density distinguish the main window from utility windows; an interactive refresh may still replace the snapshot after it verifies the currently requested surface. Applications reliably known not to be running retain their previous snapshot as stale and are reported as skipped. AX trees never enter conversation history, model context as a full tree, or relationship memory.

A usable hierarchy returns the searched semantic affordances and stable element references without capturing pixels. An omitted search result is not negative evidence for the full hierarchy. An interactive observation first reads AX without changing focus. `target_app` names one concrete launchable application; desktop-scope labels such as “当前桌面”, “屏幕”, or “前台应用” are normalized to an empty application target and never sent through dynamic AX application resolution or focus. Some applications expose only their application menu or an unrelated auxiliary window while in the background; if the first tree has no `AXWindow` or lacks sufficient evidence for the query, Body activates the requested application once, verifies it without repeatedly stealing focus, then force-refreshes AX once before considering pixels. After observation, Body restores the previously frontmost application only when the observed target is still frontmost; a user-initiated foreground change is never overwritten. Activation raises and unminimizes exposed AX windows, and Launch Services is used before the `AXFrontmost` fallback so an existing window on another Space is brought to the active Space rather than merely changing the menu-bar owner. A matching frontmost process is not sufficient: Body also verifies a normal on-screen window on the current Space through Core Graphics, with bounded AX window metadata as the no-pixel fallback. Pixel capture is deferred until that surface check succeeds; a verified focus failure returns structured partial evidence without capturing another application's screen. The post-focus AX read begins immediately instead of applying the visual-capture settle delay. A menu or utility-window match is not evidence that the requested application page was observed. If QQ, WeChat, or Music still exposes no application window after the focused retry, Body reports the target surface as unverified and does not attach a screenshot of whichever other application happens to remain visible. Each AX read has a four-second sub-budget so the background read, focus check, and forced retry remain inside the 14-second desktop-command deadline. The retry is limited to the interactive observation path; manual and end-of-session full-index refreshes remain background-only and never focus applications. Missing permission, an unsupported app, an empty or semantically insufficient hierarchy after that retry, an expired cache that cannot be refreshed, or an API failure falls back to a focused screenshot inside the same desktop command. Once the router has verified that explicit application surface, application-scoped screenshot capture skips redundant System Events, running-application, and Dock discovery. That visual frame retains the bounded AX slice and its insufficiency reason, avoiding a second overwrite-prone observation round trip.

Screenshot observation and Accessibility structure reading are independent permissions. Disabling screenshot observation prevents pixel capture, local OCR, Brain image input, and observe-model image input, but an application-scoped observation may still read and retry the named application's AX hierarchy when Accessibility is enabled. With screenshots disabled, an insufficient AX result remains structured and never falls back to pixels; a desktop-scoped observation without a concrete `target_app` reports that an application target is required. When both permissions are disabled, observation is unavailable.

Composite controls may expose their visible label only through a descendant text node. Search therefore derives a bounded display label for an unlabeled actionable ancestor and may build its reviewable reference from application identity, hierarchy path, and screen geometry; execution still re-resolves the live hierarchy uniquely and fails closed. Collection-oriented searches identify the matched `AXGrid`, `AXList`, `AXOutline`, table, or equivalent container, return one bounded logical item per currently instantiated direct branch, and report whether that item set is complete. Read-only exhaustive results carry the collection name once and each item label once, allocate the character budget across all returned items, and may return up to 64 items without executable references; this is an AX-instantiated/visible set, not an assertion about virtualized off-screen library content. `collection_complete` reports item coverage separately from `collection_labels_complete`; any budget-truncated label makes an exhaustive name query insufficient and exposes a truncation count. A complete read-only collection result can answer without pixels. An exhaustive collection query that exceeds the bounded result cannot be labeled sufficient.

Electron and HTML-backed native applications may expose a visible collection row with bounds and descendant text but no reliable native activation. Such a row may become a geometry-backed semantic affordance only when its application, live hierarchy path, unique collection branch, reviewed descendant label, and screen bounds are all bound into the reference. Finder additionally binds the descendant `file://` URL, so a same-name item substituted at the same geometry is rejected. At execution, Body re-resolves the live row, rechecks the descendant identity and bounds, and only then asks Human Ops' CoreGraphics dispatcher to click its live center. QQ conversation rows use this verified geometry even when their Electron wrapper advertises `AXPress`, because that action can return success without changing the selected conversation. For a QQ conversation row, a live matching content-pane header plus a visible editor proves that the target is already active; execution then returns a verified no-op instead of repeating the non-idempotent row click. `AXShowMenu` is never reinterpreted as a normal click. A spelling-near label is surfaced only as a clarification candidate and never silently replaces an action target.

An exposed `AXPress` proves that an action is available, not that its product meaning is “open.” Known effectful controls carry an `activation_effect` guard. In particular, a Music album card's `AXPress` starts playback; it is omitted as an affordance and the search is insufficient unless the query explicitly asks to play or pause media. Nouns such as Chinese “播放列表” and English “playlist” never count as playback verbs. Music's “Get Info” menu command carries `track_info_dialog`: it opens information for the selected track and is rejected as evidence or an action for album details.

Finder file items keep selection and opening as separate reviewed semantics. A verified-geometry click selects the logical item; only a current native `AXOpen` action is exposed with `activation=open` and may be described or executed as opening that item.

Native `AXShowMenu` is exposed only as `activation=show_menu`. It opens the reviewed target's context menu and always requires a fresh observation before a later menu command can be proposed; it never proves that any command inside that menu already ran.

Closed menu items without visible geometry are de-ranked against visible page controls, and explicit role mismatches or otherwise insufficient semantic results retain the AX slice while also falling back to visual evidence. AX action names such as `AXOpen`, `AXPress`, and `AXShowMenu` are parsed as actions rather than mistaken for roles. For an action query, only reviewable targets tied at the highest semantic score count as ambiguous; a weaker shared suffix cannot make an exact target non-executable. A structurally proven near-name ambiguity can skip pixel fallback and request user confirmation directly. When one action query still matches multiple equally strong executable elements, the result is insufficient, executable references are withheld, and Brain must narrow the next AX query by collection, role, or semantic path instead of guessing.

Browser tasks follow the user's explicit choice of Playwright or human operation. When the user has not chosen, Brain defaults to Playwright without asking which execution mode to use. The settings page lists local Chrome profiles and stores one unambiguous profile-directory name as the Playwright default. A profile explicitly named in the current task overrides that saved default; Brain asks for a profile only when neither exists or when execution proves the saved profile invalid. The choice remains valid only while the capability and surface stay unchanged.

A bounded task loop may continue `think` and `observe` decisions before authorization. The chat request's bounded `max_reasoning_steps` setting (one to twenty, default ten) is one task-wide budget shared by initial and follow-up Brain calls, corrections, observations, and post-action continuation; approval does not reset it. It stops on a proposal, user input requirement, terminal result, contradiction, or exhausted budget. After approval, continuation is controlled only by the proposal's explicit `continue_after_approval` value or its structured nonterminal `goal.next`; user wording never overrides a terminal state. Post-action continuation can consume structured results without a screenshot, but every later side effect receives its own proposal and authorization record.

Computer-use observation records a compact `route_decision` for the selected AX, local OCR, Brain vision, independent observe-model, or unavailable path. The same task retains at most a bounded, redacted route history and folds consecutive equivalent outcomes into a repeat count. Brain may use this feedback to avoid repeating an unchanged insufficient observation, but route history never expands capabilities, weakens verification, or bypasses Human Ops. Raw screenshots, OCR text, and screen content do not enter this learning state.

Every executed action is verified whether or not Brain continuation was requested. Verification uses the cheapest reliable evidence first: action result, platform focus or application state, Accessibility/DOM, and Playwright output. Visual observation is a fallback for missing structure or semantic results that event delivery cannot prove. Pressing Enter with expected text does not prove that a message appeared.

Click delivery and foreground focus prove dispatch, not the intended destination or page transition. Unless the executor supplies an independently verified postcondition, a click continuation performs a fresh outcome observation, preferring refreshed Accessibility evidence before pixels.

### Visual Evidence

Application AX observation first attempts to read the named external process without changing focus. When the process exposes no window hierarchy in the background, the bounded interactive retry described above may temporarily activate it before AX is read again. A visual-only application capture also activates and verifies the target; a focus failure is returned as explicit partial evidence instead of silently capturing whichever app was already frontmost. Every returned application frame binds the requested `target_app` at both the frame and active-observation levels, in addition to the independently verified focus and Accessibility application identities. Every pixel capture temporarily hides Ipet and waits for the compositor before reading the screen, then restores it without raising or activating it. When a fresh same-process AX snapshot provides target-window geometry, application capture crops to that window before pixels reach Brain while preserving the macOS screen origin and image scale used for coordinate conversion; stale geometry is never trusted. This prevents the chat/worklog window or unrelated applications from obscuring or leaking into the target evidence. Before an AX-insufficient application screenshot is sent to any model, the backend may run macOS Vision OCR locally. The helper returns bounded normalized text boxes, but the complete OCR text and box list remain process-local. The local search reuses Brain's current short `observe.ax_query`, exposes a separate compact `visual_search` status, and returns at most eight matching labels. Only one strong unique action match carries a deterministically converted macOS screen point; duplicate, weak, secondary, icon-only, or missing matches expose no coordinates and retain the existing screenshot fallback. The full OCR result never enters SSE events, conversation history, durable memory, or the persistent AX index.

Body records screenshot size, screen layout, and coordinate space. Direct-image proposals use `image_pixels`; the backend validates and converts them to `macos_screen_points` before authorization. Unknown, incomplete, contradictory, or out-of-bounds coordinates are not executable.

When the independent observe model is disabled, the bounded screenshot goes only to the immediately following Brain call and is then dropped. When explicitly enabled, the observe model returns bounded natural language for Brain. Screenshots are not written to conversation history, memory, or later text-only turns.

Structured observation may include `surface`, searched `affordances`, `chat_context`, a compact `ax_search` index, a compact `visual_search` status, and visible coordinate-bearing candidates. Negative evidence cannot create an affordance merely because the goal mentions it, and a bounded AX search slice cannot establish that an unreturned element is absent. Any AX search marked insufficient or stale withholds every executable reference from Brain; its remaining elements are context only until a fresh sufficient observation succeeds. A `visual_search` click affordance exists only for one strong unique OCR text-box match to the current query; multiple occurrences remain contextual and never become an executable coordinate.

Accessibility references include the authorized application identity, semantic attributes, bounded ancestry and path evidence, geometry, and an integrity fingerprint. They are not persistent object handles. At execution time Body focuses the authorized app, rebuilds the current hierarchy, and requires one unique matching element. A stale, modified, cross-application, or ambiguous reference fails closed and never silently becomes a coordinate click. Secure text values are not included in structured observation.

Native focus plus keyboard-event delivery does not prove that typed text appeared in the intended field. After targeted delivery, Body re-resolves the signed editor, waits for event propagation, and compares its live AX value exactly without returning that value to the model. The executor sets `postcondition_verified` only when the value and focus match; for chat input it additionally re-verifies the intended conversation. A verification failure is reported after the single delivery and never triggers a second System Events typing attempt. A continuing `type_text` stage still uses post-action observation when native value verification is unavailable; applications without content AX use the focused visual fallback.
An Enter/Return proposal immediately following `type_text` is held back unless the complete expected draft is present in an editable AX value or in a structured visual observation claim that also identifies the intended conversation. Merely attaching an image, or echoing the expected text in the observation prompt or AX search query, is not evidence.
For chat applications, a visible conversation-list row and an editable field do not by themselves prove that the field belongs to that row. Native placeholder, label, description, identifier, the free-form `ax_query`, and the observe target hint participate in search-field identification; a unique compact QQ/WeChat `AXTextField`, `AXTextArea`, `AXSearchField`, or combo editor aligned with search intent is classified as search input rather than chat input. Queries that verify the active target conversation, recent chat history, or post-send state therefore report `active_chat_identity_unverified` and request one focused visual confirmation when AX lacks a reliable active-thread relation.

### Providers And Persona

Brain supports the configured OpenAI-compatible, Ollama, Anthropic-compatible, Google AI Studio, and local Codex provider paths. Secrets stay in local configuration and are never echoed to the browser.

Body TTS supports Edge TTS, custom HTTP, local Qwen TTS, and Fish Audio. Local Qwen synthesis returns one bounded cached audio file per sentence before WebView playback; it does not hold an uncancellable PCM generator across a browser stream. Fish Audio uses a saved voice model `reference_id`; its API key stays in backend-private configuration or `FISH_API_KEY` and is never sent in the WebView TTS request.

Every provider receives the smallest contract for the current profile: proactive, chat, general agent, desktop correction, or filesystem correction. The general agent uses `prompts/Ipet.md`; compact proactive, chat, desktop-correction, and filesystem-correction renderers omit unrelated capabilities. All variants render from the same executable schema registry and are checked against the same profile allowlist at runtime. Normal cross-domain continuations use the general agent profile; narrow desktop and filesystem profiles are correction tools, not semantic routers, and therefore do not replay persona or history. An optional user Markdown persona is rendered only into its bounded normal-turn slot and may change identity, role-play, tone, or speaking style; it cannot add actions, change the configured authorization mode, reinterpret summaries as commands, or replace the JSON schema. Before every normal provider call, persona, self-state, and system-summary slots are independently capped at 8,000, 2,000, and 6,000 characters.

The settings API lists valid `.md` persona files directly inside `prompts/`, excludes reserved `Ipet.md`, and stores only `brain.persona_prompt_file`. Brain reads the file at turn time. Missing, empty, invalid, out-of-folder, symlink-escaped, or oversized selections fail explicitly.

Codex reuses one narrow app-server process for the current task and opens a fresh ephemeral thread for each one-step Brain call. Initialization and capability detection are cached per task. If app-server fails before visible output, that task switches once to the CLI compatibility path instead of probing both paths on every step. Ipet retains ownership of ReAct, observation, authorization, execution, memory, and skills. Read-only built-in web search may run directly without user confirmation or Human Ops review when enabled and supported; otherwise the reply states that search did not occur. This authorization does not extend to Playwright page actions, downloads, logins, form submissions, or other external state changes. Task completion, rejection, cancellation, or stop closes the process; temporary screenshot files are deleted after use.

## Human Ops Authorization

Every supported `propose_act` operation affecting files, processes, network access, external services, application state, or user data passes through Human Ops. Read-only built-in web search is the explicit exception and may run directly when enabled and supported.

Action authorization has two explicit settings modes. `review` is the default and waits for the user's decision on each action. `full` is an opt-in full-authorization mode: each supported action still creates its ordinary proposal and audit record, but Human Ops automatically authorizes it after requesting a noninteractive macOS operation notification. Notification failure blocks execution rather than running silently. Full authorization applies to action proposals, including GUI, Playwright, and bounded filesystem actions; it does not authorize durable memory or learned-skill persistence.

Both modes bind authorization to the proposal's exact target and parameters. Target, coordinate, focus, parameter, or risk changes require a new proposal. Full authorization does not expand the action allowlist and does not bypass target focus checks, Accessibility reference re-resolution, Playwright restrictions, filesystem roots, size limits, or post-action verification. When a click or text action lacks a verified postcondition, an identical click fingerprint/coordinate or the same text directed to the same stable input identity cannot be replayed unchanged by the continuation loop. The input identity uses application, role, signed input kind, semantic attributes, and live bounds, so post-input path/fingerprint churn or changing `replace_existing` cannot bypass the fuse. Brain must first alter the blocking UI state, use a newly observed semantic target, or stop as blocked.

In review mode, the user may approve, reject, reject with guidance, or approve with constraints. On macOS, the active proposal is delivered through a time-sensitive, actionable `UNUserNotificationCenter` application notification with visually explicit Approve and Reject actions. The notification is retained in Notification Center until the user decides or the approval times out. A local helper returns only the proposal id and decision through Qt; it never executes the action. The result is accepted only while that proposal is still pending. Permission denial, dismissal, delivery failure, helper failure, and timeout reject the proposal.

In full mode, the chat stop control remains active throughout notification, execution, verification, and continuation. A stop received before dispatch prevents the action and invalidates its record. A stop received while an atomic click, key delivery, application launch, browser operation, or filesystem mutation is already in flight may not undo that operation, but it prevents every later step and reports the in-flight result as uncertain. The independent full-authorization safety cap matches the global maximum task budget of 20 actions; the count travels with the task and is decremented before every notification and dispatch. Reaching zero blocks the chain instead of recursively creating more actions. Brain output alone never selects, resets, or broadens full authorization.

## Execute

Body executes only the authorized action and returns bounded evidence. Execution uses the narrowest platform API, avoids broad traversal, keeps local state out of Git, preserves unrelated work, and reports failures as facts.

- Native click, text, and key actions establish and verify `target_app` focus before input. Activation prefers AppKit when available, then Launch Services, the application's own settable `AXFrontmost` attribute with AX window raise/unminimize, and finally System Events; the final frontmost identity check remains mandatory.
- Backend-to-Body desktop commands are atomically enqueued in one nonce-named, protocol-versioned file per request instead of sharing one overwrite-prone mailbox. Queue entries without the current protocol marker or a deadline are rejected. The desktop host ingests the complete queue on each poll and remembers a bounded window of consumed nonces. Potentially blocking native actions are serialized on the desktop worker, while active vision stays on the Qt poller thread because screen capture and QtWebEngine-backed surfaces may only be touched from the application UI thread. It checks the deadline at dispatch and again immediately before focus, click, text, key, launch, notification, or observation effects. A timed-out request removes its still-queued file, while an expired or replayed request cannot execute its UI side effect. Serialized native Accessibility acquisition also has bounded foreground and background waits. The retired `/native-decision` compatibility endpoint returns immediately and cannot occupy the desktop worker with a long-running system dialog.
- For dynamically resolved macOS GUI applications, semantic click uses the element's exposed `AXPress`, focus, or selection operation. Semantic `type_text` is exposed only when the live element reports a settable `AXFocused` attribute; read-only `AXTextField` labels are not typing targets. It first resolves and verifies the authorized editable element, requests native AX focus, and tolerates the short asynchronous focus propagation used by Electron. Application-level `AXFocusedUIElement` identity is accepted as independent focus evidence. If the field still does not report focus, Body may click only the center of that same re-resolved editable element and must then verify focus again before delivering text. `replace_existing=true` requires that same reviewed reference and a verified target PID. Body first assigns the replacement through the element's settable `AXValue` and then polls the live value for an exact postcondition. Chromium and Electron may apply an accepted `AXValue` asynchronously, so an accepted mutation is never followed by keyboard delivery of the same text; only an unsupported or rejected semantic operation may fall back to targeted Command-A plus replacement text, or targeted Backspace when the replacement is empty. It never degrades to a global shortcut, and a successful event dispatch without the exact postcondition remains unverified. Coordinate input remains a fallback only when observation produced no usable semantic reference.
- Finder view-mode containers such as icon, list, column, and gallery view are normalized as the current file collection. Exact selection returns one item rather than requiring the complete collection in the action payload. A file child exposing `AXOpen` is never invoked for selection: Body signs a reviewed single-click hit-test reference on its enabled geometry, while explicit open and context-menu intents retain their distinct native actions and file-URL verification.
- QQ and WeChat message entry binds `target_app`, `intended_chat`, the full draft, and the reviewed editable `ax_ref` as one immutable task-level type/send transaction. The signed reference classifies a reviewed search editor as `input_kind=search_field`; only that class may accept search text without a recipient binding. An unlabeled compact single-line editor keeps that search signature only when its verified geometry lies in the top region of a sufficiently large main window; a field in a small login window or the lower composer region remains a chat-message target. Every other editable QQ/WeChat reference is signed fail-closed as `input_kind=chat_message`. These integrity-bound fields are forwarded unchanged through the Backend-to-Body desktop command boundary. Observe, click, launch, and other intermediate continuation steps cannot discard or replace a message transaction; Enter/Return consumes the stored transaction. Immediately before delivery, Body requires the target PID to still be frontmost, the exact editor to be focused, and an independently identified title/header—not an arbitrary same-name content node—to match the intended conversation. A WebArea shared by the title and editor is allowed, while list/scroll/content containers found only on the candidate branch are rejected. In nested Electron trees, the title must come from the non-composer branch with the deepest shared chat-pane ancestry before its top row is compared; a shallower application toolbar cannot masquerade as the active recipient. Flat WebArea trees retain the bounded top-row fallback. Chat text and Enter events use `CGEventPostToPid`; they never fall back to global System Events delivery. A stable input path in a different conversation is rejected.
- `launch_app` resolves the authorized application through macOS application metadata and Launch Services; it does not synthesize a visual click.
- Playwright accepts only authorized navigation, snapshot, stable element-ref, text, key, and tab operations. Arbitrary evaluation, shell fragments, filesystem URLs, invented selectors, and model-supplied runtime flags are rejected.
- Playwright uses the selected Chrome profile in place only when the bounded attach contract is satisfied; otherwise it uses an isolated Ipet-owned snapshot and never writes the source profile. Unknown or ambiguous profiles fail explicitly.
- A successful Playwright return proves the CLI operation, not that the user visually saw the page.

Filesystem execution exposes exactly `file_list`, `file_read`, `file_write`, `file_mkdir`, `file_copy`, `file_move`, and `file_delete`. Each receives its own proposal and authorization record and resolves inside the project root or explicitly configured roots.

The executor rejects protected local state, paths outside allowed roots, and final symbolic links. Text reads and writes are bounded UTF-8. Writes require explicit overwrite permission; copy and move never overwrite; delete handles one regular file or empty directory and never recurses. Execution uses direct filesystem APIs rather than model-supplied shell commands.

Changed risk or repeated failure returns to Human Ops or stops; the executor does not silently invent a fallback action.

If an action succeeds but the post-action continuation pipeline raises an internal error, the task is marked `continuation_failed`. The failed phase and sanitized error remain in the terminal response instead of being overwritten by the earlier action-success text; the completed side effect is still reported separately from the failed continuation.

## Memory And Skills

Durable memory records its source, visible reason, scope, retention expectation, and privacy constraints. Learned procedures have no active Brain decision until a reviewed persistence path exists; a future implementation must record trigger, bounded procedure, required approvals, and verification method.

Memory & Skills never stores raw screenshots, generated audio, local secrets, or unreviewed destructive procedures.

The settings Memory console lists saved records, process-local pending candidates, and open loops. User-initiated edits, forgetting, resolving, and snoozing are explicit console operations. Model-originated writes and status changes always use Human Ops review even if an older local configuration says memory review is disabled.

## Observe Result And Summary

After execution, Body records enough evidence to distinguish `succeeded` from `verified`: return status, relevant platform or UI state, durable identifiers, authorization mode, and bounded errors.

Each non-trivial turn ends with what changed, what was verified, what remains uncertain, and the next useful step.

## Local State

Local-only configuration, heartbeats, caches, generated audio, conversation state, logs, virtual environments, and debug output remain ignored. Product cleanup never deletes user data implicitly; destructive cleanup is a separate Human Ops action.
